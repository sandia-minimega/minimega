# Chapter 8: Command and control

Every VM in the sandwich runs miniccc, and you already used it. The ping in
[chapter 3](03-router-sandwich.md) and every `router ... commit` went through
it. This chapter covers the whole command and control API on the sandwich. In
this chapter you do these tasks:

- List the connected agents.
- Run commands and read their output and exit codes.
- Restrict commands to one VM.
- Start a program in the background and kill it.
- Push a script into a guest and fetch a file back.
- Mount the filesystem of a guest on the host.
- Open a TCP tunnel through a guest.
- Clean up.

At the end, the sandwich is unchanged, and you can drive its guests without a
network path to any of them.

It assumes the running sandwich from [chapter 3](03-router-sandwich.md).
Earlier chapters issued `cc` commands and set a filter. Before you start, run
these commands so that the command ids restart at 1:

```minimega
minimega$ clear cc filter
minimega$ cc delete command all
minimega$ clear cc responses
```

[Command and control](../../articles/cc.md) is the guide behind the chapter. It
covers what the chapter leaves out: containers, TCP clients, tags pushed from
the guest, and plumbing.

## How it works

Each KVM VM that you launch with `vm config backchannel true`, the default, gets
a virtio-serial port named `cc`. The miniccc agent inside the guest opens that
port and talks a small protocol over it. No IP address is involved. The agents
connected before the router handed out a single lease. Agents send a heartbeat
every few seconds, and `vm info` reports whether an agent sent a heartbeat
recently:

```minimega
minimega$ .columns name,cc_active vm info
name     | cc_active
router   | true
vm-left  | true
vm-right | true
```

`cc` alone counts the connected agents. `cc clients` lists what each agent
reported: its UUID, hostname, OS, architecture, addresses, and capabilities.
Each heartbeat refreshes this data:

```minimega
minimega$ cc clients
uuid                                 | hostname | arch  | os    | ip           | mac   | capabilities
5f2e...                              | ...      | amd64 | linux | [10.0.0.37]  | [...] | auto-update
...
```

Two rules shape everything else. First, minimega queues commands and delivers
them to matching agents in the order that you issued them. Therefore "send a
file, run it, fetch the result" happens in that order. Second, a command stays
queued until you delete it. An agent that reconnects runs every command that is
still in the queue. A VM that you launch later and that matches the filter does
the same.

## Running a command

`cc exec` queues a command for every agent that matches the current filter.
There is no filter yet, so this runs on all three VMs. Nothing is printed.
minimega writes the output to a response directory on the host, and you read it
back with `cc responses`:

```minimega
minimega$ cc exec cat /etc/motd
minimega$ cc commands
```

`cc commands` lists every command issued in the namespace. It shows the id of
the command, what the command runs, how many agents responded, and the filter of
the command. The commands at the start of the chapter set the counter back, so
this command is id 1. Its `responses` column reaches 3 after all agents
reported. Read the responses:

```minimega
minimega$ cc responses 1
1/<uuid of router>/stdout:
minirouter built with vmbetter on Wed Sep 16 14:02:11 UTC 2026

1/<uuid of vm-left>/stdout:
miniccc built with vmbetter on Wed Sep 16 13:41:07 UTC 2026

...
```

Each block is one file under
`/tmp/minimega/files/sandwich/miniccc_responses/1/<uuid>/`. minimega writes
`stdout` and `stderr` only when they are not empty. It writes `exitcode` only
for `cc exec` and `cc exec-once`. Add `raw` to print only the contents without
the path headers. Quote arguments that contain spaces or characters that the
prompt interprets. To use a shell pipeline in the guest, run the shell:

```minimega
minimega$ cc exec sh -c "ip -4 addr show eth0 | grep inet"
```

## Restricting commands to some VMs

`cc filter` sets `key=value` pairs that an agent must match for the commands
that you issue afterwards. `name=` matches the `name` column of `vm info`. Any
other column or a tag works the same way. `os=`, `ip=` (a single address or a
CIDR), and `uuid=` match what the agent itself reports. When you issue a
command, minimega records the filter on the command. A later change to the
filter therefore does not affect commands that are already queued.

```minimega
minimega$ cc filter name=vm-left
minimega$ cc exec ping -c 3 10.0.1.1
minimega$ cc filter
uuid | hostname | arch | os | ip | mac | tags
     |          |      |    |    |     | {"name":"vm-left"}
```

`cc filter` alone prints the filter in force, and `clear cc filter` removes it.
Several pairs combine with AND, so `cc filter os=linux name=vm-left` matches
only the left client of the sandwich. The built-in keys are `uuid`, `hostname`,
`arch`, `os`, `ip`, `mac`, and `tag`. minimega compares every other key against
the whole `vm info` cell as text. This works for single-valued columns such as
`name`, but not for list columns such as `vlan`.

## Exit codes and connectivity tests

A foreground command records its exit status. `cc exitcode <id> <vm>` prints the
status. `-1` means that the program did not start at all, usually because the
agent did not find it. `cc test-conn` asks the guest to open a TCP or UDP
connection and to retry until the wait expires. It writes the verdict to the
`stdout` of the command. The router runs an SSH server, so this test passes:

```minimega
minimega$ cc exitcode 3 vm-left
0
minimega$ cc test-conn tcp 10.0.1.1 22 wait 10s
minimega$ cc responses 4
4/<uuid of vm-left>/stdout:
10.0.1.1:22 | pass
```

## Background commands

`cc exec` waits for the program to exit before the agent moves on to the next
command. A daemon or a traffic generator that you start with `cc exec` therefore
blocks everything behind it. Start those programs with `cc background`, which
returns at once. Background commands record no exit code. Their output goes to
the log of the agent, not to a response.

```minimega
minimega$ cc background sleep 600
minimega$ cc process list vm-left
name    | uuid    | pid  | command
vm-left | 5f2e... | 1043 | sleep 600
minimega$ cc process killall sleep
```

Processes started in the background are tracked by PID. `cc process kill <pid>`
stops one process. `killall <name>` stops every process whose command line
contains the name. `cc process list all` lists the processes for every agent.
[Chapter 11](11-traffic.md) uses this to run protonuke on the clients.

If an agent reconnects, some commands must not run again. Two variants exist for
these commands. `cc exec-once` and `cc background-once` go only to the matching
agents that are connected at the moment you issue them. Use these variants for
`cc exec-once reboot`. A plain `cc exec reboot` is delivered again to the
freshly booted agent, and that agent reboots again.

## Files in and out

`cc send` queues a file for delivery. The file must be in the files directory of
minimega (`/tmp/minimega/files`, or the directory that `-filepath` sets).
minimega tries the path as given. If that fails, it tries the same path under
the subdirectory of the namespace. Put a two-line script in the files directory.
Then send the script:

```bash
$ printf 'echo hello from cc\nuname -n\n' | sudo tee /tmp/minimega/files/hello.sh
```

```minimega
minimega$ cc send hello.sh
minimega$ cc exec sh /tmp/miniccc/files/hello.sh
```

Files land under `/tmp/miniccc/files/` in the guest with the same relative path
that they had on the host. A file that already exists there is skipped, not
overwritten. Send a changed script under a new name. A command that is not on
the `PATH` of the guest is also looked up in that directory. You can therefore
run an executable script by bare name.

`cc recv` goes the other way. It takes any path on the guest, and globs also
work. The files arrive in the response directory of the command under their full
guest path. Fetch the `/etc/motd` of the image, which the build in chapter 2
wrote:

```minimega
minimega$ cc recv /etc/motd
minimega$ cc responses 9
9/<uuid of vm-left>/etc/motd:
miniccc built with vmbetter on Wed Sep 16 13:41:07 UTC 2026
```

## Prefixes

Command ids identify commands for responses and deletion. They are awkward in a
script that does not know how many commands came before. `cc prefix <name>` tags
every command issued after it. The prefix then works in place of an id:

```minimega
minimega$ cc prefix hello
minimega$ cc exec sh /tmp/miniccc/files/hello.sh
minimega$ cc recv /etc/motd
minimega$ clear cc prefix
minimega$ cc responses hello
minimega$ cc delete response hello
```

## Into the guest: mount and tunnel

Two commands turn the agent into more than a remote shell. `cc mount` mounts the
root filesystem of a VM on the host. A 9p server that is built into miniccc
serves the filesystem over the same serial channel. The mount point must exist,
and minimega must run as root. Under systemd, minimega runs as root:

```minimega
minimega$ shell mkdir -p /mnt/vm-left
minimega$ cc mount vm-left /mnt/vm-left
minimega$ shell ls /mnt/vm-left
minimega$ clear cc mount vm-left
```

Unmount the filesystem before you kill or stop the VM. `clear namespace`
unmounts it for you.

`cc tunnel` is `ssh -L` through the agent. It opens a listening port on the
host. The tunnel forwards the port through the guest to an address and port that
the guest can reach, including the guest itself. The stock image runs an SSH
server that accepts root with no password. This tunnel therefore gives you a
shell on `vm-left` with no host tap and no address at all. Run these commands:

```minimega
minimega$ cc tunnel vm-left 2222 127.0.0.1 22
minimega$ cc tunnel list vm-left
vm      | id | src port | dst       | dst port
vm-left | 1  | 2222     | 127.0.0.1 | 22
```

```bash
$ ssh -p 2222 root@localhost
```

`cc tunnel close vm-left 1` tears the tunnel down. It uses the id from the list,
and tunnel ids start at 1. The reverse form, `cc rtunnel`, is the `ssh -R`
counterpart. The guide describes it.

## Cleaning up

Responses accumulate on disk and commands stay queued until you remove them. At
the end of a session, or before you replay a script that issues its own, run
these commands:

```minimega
minimega$ clear cc filter
minimega$ cc delete command all
minimega$ clear cc responses
```

`cc delete command|response` also takes an id or a prefix. `clear cc` resets
everything at once: commands, responses, filter, prefix, and mounts. Deleting a
command does not stop a background process that it started. Use
`cc process kill` for that.

## Pitfalls

- miniccc and minimega must come from the same release. If they do not, there is
  a version mismatch, and minimega logs
  `mismatched miniccc version on <hostname>: <revision>` at connect time and
  continues. Commands can be dropped or misreported. minimega refuses an agent
  that is too old, with `miniccc client too old -- please update`. When you
  upgrade minimega, rebuild the images from [chapter 2](02-images.md).
- If the agent never connects, look at `cc_active` in `vm info`. Read the log of
  the agent in the guest (`/miniccc.log` in the stock images). Also make sure
  that you launched the VM with `vm config backchannel true`. A
  `vm config virtio-ports` port named `cc` collides with the backchannel.
  [Chapter 10](10-troubleshooting.md) explains the full procedure.
- Windows guests run miniccc as a service and need the virtio-serial driver
  first. Wrap commands in `cmd /c` so that the shell resolves them. See
  [Windows guests](../../articles/windows.md).

## What you built

- The sandwich, unchanged, and a clear picture of the channel that every
  `cc` and `router` command uses.
- Responses, exit codes, and a connectivity test from `vm-left`, a script sent
  into it, and a file fetched back. You read all of these by id and by prefix.
- A shell on `vm-left` through a `cc` tunnel, with no network between host
  and guest.
