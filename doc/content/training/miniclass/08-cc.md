# Chapter 8: Command and control

Every VM in the sandwich runs miniccc, and you have already used it: the
ping in [chapter 3](03-router-sandwich.md) and every `router ... commit`
went through it. This chapter covers the whole command and control API on
the sandwich. You list the connected agents, run commands and read their
output and exit codes, restrict commands to one VM, start a program in the
background and kill it, push a script into a guest and fetch a file back,
mount a guest's filesystem on the host, open a TCP tunnel through a guest,
and clean up. At the end the sandwich is unchanged, and you can drive its
guests without a network path to any of them.

It assumes the running sandwich from [chapter 3](03-router-sandwich.md).
[Command and control](../../articles/cc.md) is the guide behind the chapter
and covers what is left out here: containers, TCP clients, tags pushed from
the guest, and plumbing.

## How it works

Each KVM VM launched with `vm config backchannel true`, the default, gets a
virtio-serial port named `cc`. The miniccc agent inside the guest opens that
port and talks a small protocol over it, so no IP address is involved: the
agents were connected before the router had handed out a single lease.
Agents send a heartbeat every few seconds, and `vm info` reports whether one
has been heard from recently:

```minimega
minimega$ .columns name,cc_active vm info
name     | cc_active
router   | true
vm_left  | true
vm_right | true
```

`cc` alone counts the connected agents, and `cc clients` lists what each one
reported: its UUID, hostname, OS, architecture, and its addresses, refreshed
on every heartbeat:

```minimega
minimega$ cc clients
uuid                                 | hostname | arch  | os    | ip           | mac
5f2e...                              | ...      | amd64 | linux | [10.0.0.37]  | [...]
...
```

Two rules shape everything else. Commands are queued in minimega and
delivered to matching agents in the order you issued them, so "send a file,
run it, fetch the result" happens in that order. And a command stays queued
until you delete it: an agent that reconnects, or a VM launched later that
matches the filter, runs every command still in the queue.

## Running a command

`cc exec` queues a command for every agent that matches the current filter.
There is no filter yet, so this runs on all three VMs. Nothing is printed:
the output is written to a response directory on the host and read back
with `cc responses`:

```minimega
minimega$ cc exec cat /etc/motd
minimega$ cc commands
```

`cc commands` lists every command issued in the namespace with its id, what
it runs, how many agents have responded, and the filter it was issued
under. The three commands of the router commit are ids 1 to 3, so this one
is id 4, and its `responses` column reaches 3 once all agents have reported.
Read them:

```minimega
minimega$ cc responses 4
4/<uuid of router>/stdout:
minirouter built with vmbetter on Wed Sep 16 14:02:11 UTC 2026

4/<uuid of vm_left>/stdout:
miniccc built with vmbetter on Wed Sep 16 13:41:07 UTC 2026

...
```

Each block is one file under
`/tmp/minimega/files/sandwich/miniccc_responses/4/<uuid>/`: `stdout`,
`stderr` when it is not empty, and `exitcode`. Add `raw` to print only the
contents without the path headers. Quote arguments that contain spaces or
characters the prompt would interpret; to use a shell pipeline in the guest,
run the shell:

```minimega
minimega$ cc exec sh -c "ip -4 addr show eth0 | grep inet"
```

## Restricting commands to some VMs

`cc filter` sets `key=value` pairs that an agent must match for the commands
issued afterwards. `name=` matches the `name` column of `vm info`, and any
other column or a tag works the same way; `os=`, `ip=` (a single address or
a CIDR) and `uuid=` match what the agent itself reports. The filter is
recorded on each command as it is issued, so changing it later does not
affect commands already queued.

```minimega
minimega$ cc filter name=vm_left
minimega$ cc exec ping -c 3 10.0.1.1
minimega$ cc filter
uuid | hostname | arch | os | ip | mac | tags
     |          |      |    |    |     | {"name":"vm_left"}
```

`cc filter` alone prints the filter in force and `clear cc filter` removes
it. Several pairs combine with AND, so `cc filter os=linux name=vm_left`
would match the sandwich's left client only. Keys other than the built-in
ones (`uuid`, `hostname`, `arch`, `os`, `ip`, `mac`, `tag`) are compared
against the whole `vm info` cell as text, which works for single-valued
columns such as `name` but not for list columns such as `vlan`.

## Exit codes and connectivity tests

A foreground command records its exit status, which `cc exitcode <id> <vm>`
prints; `-1` means the program could not be started at all, usually because
it was not found. `cc test-conn` asks the guest to open a TCP or UDP
connection and retry until the wait expires, and writes the verdict to the
command's `stdout`. The router runs an SSH server, so this passes:

```minimega
minimega$ cc exitcode 5 vm_left
0
minimega$ cc test-conn tcp 10.0.1.1 22 wait 10s
minimega$ cc responses 6
6/<uuid of vm_left>/stdout:
10.0.1.1:22 | pass
```

## Background commands

`cc exec` waits for the program to exit before the agent moves on to the
next command, so a daemon or a traffic generator started with `cc exec`
blocks everything behind it. Start those with `cc background`, which
returns at once. Background commands record no exit code and their output
goes to the agent's log rather than to a response.

```minimega
minimega$ cc background sleep 600
minimega$ cc process list vm_left
name    | uuid    | pid  | command
vm_left | 5f2e... | 1043 | sleep 600
minimega$ cc process killall sleep
```

Processes started in the background are tracked by PID;
`cc process kill <pid>` stops one, `killall <name>` every one whose command
line contains the name, and `cc process list all` lists them for every
agent. [Chapter 11](11-traffic.md) uses this to run protonuke on the
clients.

Two variants exist for commands that must not run again when an agent
reconnects. `cc exec-once` and `cc background-once` go only to the matching
agents connected at the moment you issue them, which is what you want for
`cc exec-once reboot`: a plain `cc exec reboot` would be re-delivered to
the freshly booted agent, which would reboot again.

## Files in and out

`cc send` queues a file for delivery. It must live in minimega's files
directory (`/tmp/minimega/files` unless the daemon runs with another
`-filepath`); minimega tries the path as given and, if that fails, the
same path under the namespace's subdirectory. Put a two-line script there
and send it:

```bash
$ printf 'echo hello from cc\nuname -n\n' | sudo tee /tmp/minimega/files/hello.sh
```

```minimega
minimega$ cc send hello.sh
minimega$ cc exec sh /tmp/miniccc/files/hello.sh
```

Files land under `/tmp/miniccc/files/` in the guest with the same relative
path they had on the host, and a file that already exists there is skipped,
not overwritten; send a changed script under a new name. A command that is
not on the guest's `PATH` is also looked up in that directory, so an
executable script can be run by bare name.

`cc recv` goes the other way: any path on the guest, globs included, and the
files arrive in the command's response directory under their full guest
path. Fetch the image's `/etc/motd`, which chapter 2's build wrote:

```minimega
minimega$ cc recv /etc/motd
minimega$ cc responses 9
9/<uuid of vm_left>/etc/motd:
miniccc built with vmbetter on Wed Sep 16 13:41:07 UTC 2026
```

## Prefixes

Command ids are the handle for responses and deletion, and they are awkward
in a script that does not know how many commands came before.
`cc prefix <name>` tags every command issued after it, and the prefix then
works in place of an id:

```minimega
minimega$ cc prefix hello
minimega$ cc exec sh /tmp/miniccc/files/hello.sh
minimega$ cc recv /etc/motd
minimega$ clear cc prefix
minimega$ cc responses hello
minimega$ cc delete response hello
```

## Into the guest: mount and tunnel

Two commands turn the agent into more than a remote shell. `cc mount`
mounts a VM's root filesystem on the host, served by a 9p server built into
miniccc over the same serial channel; the mount point must exist and
minimega must be running as root, which it is under systemd:

```minimega
minimega$ shell mkdir -p /mnt/vm_left
minimega$ cc mount vm_left /mnt/vm_left
minimega$ shell ls /mnt/vm_left
minimega$ clear cc mount vm_left
```

Unmount before you kill or stop the VM; `clear namespace` does it for you.
`cc tunnel` is `ssh -L` through the agent: a listening port on the host,
forwarded through the guest to an address and port the guest can reach,
including itself. The stock image runs an SSH server that accepts root
with no password, so this gives you a shell on `vm_left` with no host tap
and no address at all:

```minimega
minimega$ cc tunnel vm_left 2222 127.0.0.1 22
minimega$ cc tunnel list vm_left
vm      | id | src port | dst       | dst port
vm_left | 1  | 2222     | 127.0.0.1 | 22
```

```bash
$ ssh -p 2222 root@localhost
```

`cc tunnel close vm_left 1` tears it down, using the id from the list;
tunnel ids start at 1. A reverse form, `cc rtunnel`, is in the command set
but does not currently work; the guide explains.

## Cleaning up

Responses accumulate on disk and commands stay queued until you remove
them. At the end of a session, or before you replay a script that issues
its own:

```minimega
minimega$ clear cc filter
minimega$ cc delete command all
minimega$ clear cc responses
```

`cc delete command|response` also takes an id or a prefix, and `clear cc`
resets everything at once: commands, responses, filter, prefix and mounts.
Deleting a command does not stop a background process it started; use
`cc process kill` for that.

## Pitfalls

- **Version mismatch.** miniccc and minimega must come from the same
  release. When they do not, minimega logs
  `mismatched miniccc version on <hostname>: <revision>` at connect time
  and carries on, but commands may be dropped or misreported, and an agent
  that is too old is refused with `miniccc client too old -- please update`.
  Rebuild the images from [chapter 2](02-images.md) whenever you upgrade
  minimega.
- **The agent never connects.** Check `cc_active` in `vm info`, the
  agent's log in the guest (`/miniccc.log` in the stock images), and that
  the VM was launched with `vm config backchannel true`. A
  `vm config virtio-ports` port named `cc` collides with the backchannel.
  [Chapter 10](10-troubleshooting.md) has the full walk.
- **Windows guests** run miniccc as a service and need the virtio-serial
  driver first; wrap commands in `cmd /c` so the shell resolves them. See
  [Windows guests](../../articles/windows.md).

## What you built

- The sandwich, unchanged, and a clear picture of the channel that every
  `cc` and `router` command uses.
- Responses, exit codes and a connectivity test from `vm_left`, a script
